# 全栈学习库优化设计

版本：v4
状态：设计阶段
适用项目：`vibe-coding-glossary`

## 1. 产品定位

本项目定位为：

> 面向初学者的全栈技术认知与 AI 协作训练库。

它帮助学习者快速建立从页面、浏览器、网络、后端、数据、安全到部署的技术地图，再通过真实任务训练需求拆解、AI 引导、代码审查、测试验收和故障修复能力。

项目不把“让 AI 代写更多代码”作为目标。学习者必须先知道问题属于什么领域、技术解决什么问题、有哪些常见方案以及怎样判断结果是否正确，然后再让 AI 扩大实现效率。

核心闭环：

```text
快速认识技术
→ 建立技术之间的关系
→ 自己做一次判断
→ 引导 AI 完成小任务
→ 阅读和检查 AI 的修改
→ 运行、测试、验收
→ 根据证据修复问题
→ 把经验迁移到下一个任务
```

## 2. 目标用户与学习结果

### 2.1 目标用户

- 会使用电脑，但没有完整编程基础的初学者；
- 已经尝试 Vibe Coding，但经常不知道如何描述需求、检查代码和处理报错的人；
- 想扩展全栈技术广度，同时建立工程判断力的人。

### 2.2 学习结果

学习者完成基础路线后，应能做到：

1. 用自己的话解释常见全栈技术，知道它解决什么问题；
2. 判断一个需求涉及前端、网络、后端、数据、安全还是部署；
3. 把大需求拆成 AI 可以逐步执行的小任务；
4. 向 AI 提供项目上下文、修改边界和验收标准；
5. 看懂 AI 修改了哪些文件和关键逻辑；
6. 通过运行结果、日志、测试和差异检查判断代码是否可信；
7. 遇到问题时能提供证据，让 AI 沿着正确方向继续修复；
8. 在技术广度和主线项目深度之间建立联系。

## 3. 学习体验原则

### 3.1 初学者默认路径

首次进入时默认展示“从这里开始”，而不是让用户直接面对 12 个知识模块和主线项目的完整目录。

首条路径建议为：

```text
看懂一个页面
→ 修改一个按钮行为
→ 调用一个接口
→ 保存一条数据
→ 加入登录
→ 测试并修复一个错误
→ 完成一次 Git 提交
```

每一步都显示：预计用时、前置知识、操作动作、预期结果、失败后的检查方式和下一步入口。

### 3.2 渐进式复杂度

每个知识点按三层展开：

| 层级 | 目标 | 默认呈现 |
| --- | --- | --- |
| 快速看懂 | 知道是什么、解决什么问题 | 一句话、类比、最小 demo、关键词 |
| 动手理解 | 亲手让结果发生 | 一个操作、一个可见结果、重置入口 |
| 工程深挖 | 形成方案判断和排障能力 | 对比、取舍、故障实验、测试和部署 |

初学者先看到快速看懂和动手理解，工程深挖通过明确的“继续深入”入口展开。复杂术语在第一次出现时必须给出中文解释、英文术语、具体例子和后续用途。

### 3.3 人必须先思考

关键知识点必须提供“先想再看”环节，例如：

- 先选择保存位置；
- 先预测代码运行顺序；
- 先判断错误属于哪一层；
- 先写验收标准；
- 先比较两种技术方案。

AI 的参考分析在用户完成判断后出现。这样 AI 用来扩展思路，而不是替代技术认知。

## 4. 统一学习单元

所有模块、技术卡和 demo 都采用同一套内容结构。

### 4.1 学习单元模板

```text
你将学会什么
→ 开始前需要知道什么
→ 技术认知：它是什么、解决什么问题
→ 系统位置：它和哪些技术相连
→ 最小 demo：看见它发生
→ 动手任务：修改或补全一小部分
→ 先想再看：做一次独立判断
→ AI 任务卡：让 AI 完成一个小任务
→ 验收卡：如何确认结果正确
→ 翻车卡：常见错误和证据链
→ 工程深挖：方案、代价和适用边界
→ 主线项目：把知识用到真实功能
```

### 4.2 四类核心卡片

| 卡片 | 必须回答的问题 |
| --- | --- |
| 认知卡 | 这是什么，解决什么问题？ |
| 关系卡 | 它在系统的什么位置，和什么相连？ |
| 决策卡 | 什么时候选它，替代方案和代价是什么？ |
| AI 卡 | 怎样让 AI 使用它，重点检查什么？ |

### 4.3 单元完成标准

一个单元只有同时满足以下条件才算完成：

- 能用自己的话解释核心概念；
- 能指出它在系统中的位置；
- 能说出至少一种替代方案或限制；
- 完成一次真实交互或代码修改；
- 给 AI 提出一个带上下文和验收标准的任务；
- 检查 AI 的关键结果；
- 分析或修复一个常见错误。

## 5. Vibe Coding 能力模型

项目将 Vibe Coding 拆成六项可以训练和验收的能力：

| 能力 | 学习目标 | 页面训练方式 |
| --- | --- | --- |
| 识别问题 | 判断需求涉及的技术层 | 任务到技术地图的连线 |
| 拆解任务 | 把大需求拆成小交付物 | 主线项目步骤和任务树 |
| 提供上下文 | 说明文件、现状、约束和错误证据 | AI 任务卡模板 |
| 控制范围 | 指定允许修改的文件和不能破坏的行为 | 修改边界清单 |
| 阅读结果 | 看懂差异、数据流和关键逻辑 | 修改前后对照和逐段解释 |
| 验收修复 | 用结果、日志和测试推动迭代 | 验收卡与故障实验 |

### 5.1 AI 任务卡格式

所有 AI 示例统一包含：

```text
任务：最终想让用户看到什么
上下文：项目结构、相关文件、已有功能、当前状态
约束：允许修改什么、不能修改什么、技术限制是什么
过程：先分析、先列计划，还是直接实现
输出：需要代码、差异、测试还是解释
验收：成功、空数据、错误输入、重复操作分别应该怎样
```

示例任务必须展示“低质量提问”和“可执行提问”的差异，说明差异来自哪些上下文和约束。

### 5.2 AI 输出验收清单

每次 AI 产出后，学习者至少检查：

- 是否完成了需求和异常场景；
- 是否破坏原有功能；
- 是否处理加载、空数据和错误状态；
- 是否能重复操作且不会叠加事件或定时器；
- 是否存在硬编码地址、密钥或魔法值；
- 是否处理输入、权限和敏感数据；
- 是否有对应的运行验证或测试；
- 是否只修改了约定范围内的文件。

## 6. 技术地图设计

项目采用“12 个知识模块 + 1 个主线项目”的结构。12 个知识模块负责建立技术认知，主线项目负责把知识串成一次真实交付。入口增加“按任务学习”，让用户从真实目标进入相关模块。

### 6.1 两种入口

**按知识学习**：页面基础、JavaScript、组件化前端、前端工程、Python、网络、后端、数据、身份权限、工具链、部署和 AI 协作。

**按任务学习**：做登录、做列表、做表单、做文件上传、做管理后台、接入第三方接口、部署一个服务。

### 6.2 任务到技术的映射

以“做登录”为例，页面应显示：

```text
表单输入
→ 前端请求
→ 后端接口
→ 参数校验
→ 用户数据
→ 密码安全
→ Session 或 JWT
→ 权限判断
→ 错误提示
→ 测试和部署
```

每个节点都能跳转到对应模块的快速解释、demo、AI 任务卡和验收卡。

### 6.3 广度线与深度线

```text
广度线：快速认识完整请求链，建立技术地图
深度线：围绕一个主线项目，把关键链路做透
```

广度线不要求一次掌握全部细节，深度线在需要时补充前置知识，避免用户只会单一框架或只记住零散术语。

### 6.4 知识地图顺序与学习顺序

侧栏按技术归属分组，学习路线按依赖关系推进，两者不强行使用同一个顺序。推荐的学习顺序是：

```text
工具链最小入口
→ M1 页面基础
→ M2 JavaScript 与浏览器交互
→ M3 组件化前端
→ M4 前端工程
→ M9 网络与浏览器
→ M5 Python 后端代码基础
→ M6 HTTP 与后端工程
→ M7 数据与存储
→ M8 身份与权限
→ M10 工具链与 Git（完整章节）
→ M11 部署与运维
→ 主线项目持续推进
→ M12 AI 协作总结
```

工具链最小入口在第一天出现，只要求会进入项目、启动页面、看报错和提交一次修改；完整的依赖管理、分支、合并、冲突和回滚放到 M10 系统学习。

### 6.5 AI 协作的贯穿层与集中章

AI 协作不是学完所有技术之后才开始的内容。每个模块和每个主线项目步骤都必须包含一张 AI 任务卡、一份结果验收清单和一个常见翻车现场：

```text
技术认知
→ 自己先做判断
→ 给 AI 的任务
→ 修改边界
→ 查看差异
→ 运行和测试
→ 根据证据修复
```

M12 的作用是把一路使用过的协作方法系统整理出来，包括上下文整理、任务拆解、范围控制、代码审查、测试生成、证据化排错和可复用模板。M12 可以随时进入查看，但在推荐学习顺序中放在技术线和主线项目之后，作为 AI 协作总结章；它不是前面学习的前置条件。

## 7. 主线项目设计

原规划中的“行程管理”继续作为主线项目，新增两种模式：

### 7.1 跟做模式

- 提供目录结构和启动方式；
- 每步只引入少量新概念；
- 提供部分代码和操作提示；
- 每完成一步都能运行；
- 每步都有重置点、验收清单和常见故障。

### 7.2 挑战模式

- 只给需求、约束和验收标准；
- 学习者自己决定文件结构和技术方案；
- 完成后查看参考实现和方案对比；
- 将差异记录为一次工程复盘。

### 7.3 主线阶段

```text
需求与页面草图
→ Git 初始化和首次提交
→ 数据模型和迁移
→ 后端接口和参数校验
→ 前端页面和请求状态
→ 登录和权限
→ 测试、日志和健康检查
→ Docker、反向代理和部署
→ 故障复盘和一次迭代
```

页面教学导航使用 `project.html`，真实可运行代码放入 `examples/trip-manager/`，保证“看得懂”和“跑得起来”分开但互相对应。

## 8. 页面与交互优化

### 8.1 首页

新增或调整为以下区域：

1. “第一次来，从这里开始”主入口；
2. 三分钟技术地图预览；
3. 按知识学习和按任务学习两个入口；
4. 当前学习进度和下一步；
5. 完整 12 个知识模块地图和主线项目入口；
6. AI 协作中心和当前路线的下一步。

### 8.2 模块页

模块首屏固定展示：

- 本模块解决什么问题；
- 学完可以完成什么任务；
- 需要哪些前置知识；
- 快速看懂入口；
- 工程深挖入口；
- AI 任务入口；
- 主线项目关联步骤。

### 8.3 Demo 交互

每个 demo 都必须具备：

- 明确的操作按钮；
- 可见的结果区域；
- 解释结果的短句；
- 重置按钮；
- 失败时的检查提示；
- 不依赖控制台才能理解的反馈。

### 8.4 术语显示

首次出现的术语使用“中文解释 + 英文术语 + 具体例子”的组合。技术缩写不能连续堆叠，页面需要提供相关术语和前置知识的跳转。

## 9. 内容与代码架构

### 9.1 保留两层载体

```text
index.html                  快速认识、知识地图、交互 demo、AI 任务卡
project.html                主线项目教学导航、跟做和挑战模式
examples/trip-manager/      可真实运行的全栈示例
```

现有零依赖单文件继续承担快速学习入口。真实示例单独维护运行依赖，避免初学者为了看懂一个概念就先搭建完整环境。

### 9.2 模块元数据扩展

现有 `MODULES` 注册表继续作为模块导航的单一数据源，每个模块逐步增加：

```text
prerequisites     前置模块或概念
quickGoal         快速学习目标
taskLinks         关联任务
aiTasks           AI 任务卡
decisionCards     方案决策卡
failureCards      故障实验
projectSteps      主线项目步骤
assessment        验收项
```

新增元数据必须使用新的字段名，不覆盖已有导航字段。页面显示、路线导航和统计数据从元数据生成，避免手工数字与实际内容不一致。

## 10. 分阶段实施

### 阶段 0：设计定稿

交付本文件，确定定位、学习单元、能力模型、主线项目和验收规则。

### 阶段 1：初学者入口

- 增加“从这里开始”路线；
- 建立快速看懂 / 动手理解 / 工程深挖三层显示；
- 选 M1、M2、M6 做三个代表单元；
- 统一 demo 的操作、结果、重置和错误提示。

### 阶段 2：AI 协作训练

- 增加 AI 任务卡组件；
- 增加低质量提问与可执行提问对照；
- 增加 AI 输出验收清单；
- 增加“先想再看”判断组件。

### 阶段 3：技术地图与任务入口

- 增加任务到技术模块的映射；
- 为登录、列表、表单和部署建立任务路线；
- 把每个任务连接到认知卡、决策卡和故障卡。

### 阶段 4：主线项目

- 建立 `project.html`；
- 建立 `examples/trip-manager/`；
- 完成跟做模式、挑战模式、重置点和阶段验收；
- 为每个阶段保留 Git 提交点和故障复盘。

### 阶段 5：进度与验证

- 记录看过、做过、验收通过和能够独立修复的不同状态；
- 增加关键路径测试和页面冒烟验证；
- 增加全站搜索、术语索引和复习入口。

## 11. 验收标准

### 11.1 初学者体验

- 新用户在首屏能找到明确起点；
- 每个学习单元能在几分钟内说明目标和结果；
- 首次出现的术语有即时解释；
- demo 不依赖打开控制台才能知道是否成功；
- 出错时有下一步检查路径；
- 小屏幕下目录、卡片和代码不重叠。

### 11.2 技术认知

- 每个重点技术都有认知卡、关系卡和决策卡；
- 用户能看到技术在完整请求链中的位置；
- 每个关键主题至少有一种替代方案和适用边界；
- 广度路线和深度项目路线可以互相跳转。

### 11.3 AI 协作

- 每个重点主题都有 AI 任务卡；
- AI 任务包含上下文、约束、输出和验收标准；
- 用户先做判断，再查看 AI 参考分析；
- 每个 AI 任务都有可执行的结果检查；
- 至少有一个错误现场可以通过证据引导 AI 修复。

### 11.4 工程化

- 主线项目每一步都有可运行产物；
- 代码、测试、日志、部署和 Git 形成完整链路；
- 项目可以在另一台环境按 README 重新启动；
- 页面控制台无新增错误，重复操作不会叠加事件或定时器；
- 模块统计由注册表和实际内容计算，不依赖手写数字。

## 12. 暂不扩展的范围

为了保持初学者的认知负担可控，暂不把以下内容作为第一阶段重点：

- 完整语法百科；
- 所有框架的深度源码分析；
- 大量提示词技巧理论；
- 与主线项目无关的复杂云服务；
- 追求自动评分而牺牲解释过程的练习系统。

这些内容可以作为后续深挖资料，但不能抢占“建立技术心智、完成小任务、验收 AI 结果”这条主线。

## 13. 最终判断标准

以后每增加一个知识点、demo 或功能，都用下面的问题判断它是否值得加入：

1. 初学者能否快速知道它解决什么问题？
2. 它是否帮助学习者建立全栈技术地图？
3. 学习者是否需要先做一次自己的判断？
4. 它是否能转化为一个真实的 AI 协作任务？
5. 学习者是否能用证据验收 AI 的结果？
6. 这项能力能否迁移到主线项目或其他技术？

只有同时服务于技术认知和 AI 驾驭能力的内容，才进入主线；其余内容降为索引、补充阅读或后续阶段。
