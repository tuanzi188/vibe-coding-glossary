    盒模型 Box Model/ content-box vs border-box
    内容
    width:120
    —
    同一个 width:120px：content-box（默认）下 padding 和 border 往外撑，实际占宽 = 120 + 2×padding + 2×border；border-box 下 padding/border 算在 120 以内、内容区自己缩。现代项目几乎都全局写 *{box-sizing:border-box}，就为了「写的宽度 = 占的宽度」。
    "全局 box-sizing:border-box，别让 padding 把布局撑歪"
    选择器优先级 Specificity/ 谁写谁生效？

    这段字谁说了算

    —
    多条规则抢一个元素时，先比优先级再看书写顺序：行内 > id > 类 > 标签。取消勾选看谁接管——这就是为什么「用 !important 硬压」是坏味道：你在跟级联系统对着干。
    "别加 !important，提高选择器特异性或换 class"
    布局模式 Layout/ block · flex · grid
    12345
    同样 5 个子元素，换的是容器的 display：block 竖着堆；flex 排成一行、用 justify-content 管主轴对齐；grid 二维按列铺。一维排布用 flex、二维网格用 grid，是当前主流分工。
    "这一排用 flex + justify-content:space-between，整页网格用 grid"
    语义化 Semantic/ div 汤 vs 语义标签
    —
    两种写法长得一模一样，区别在给机器看的大纲：全 div 时读屏器 / 搜索引擎只看到一堆匿名 div；用 header/nav/main/footer 就自动产出「地标（landmark）」大纲，键盘用户能一键跳到正文。语义化不是好看，是给辅助技术和 SEO 留结构。
    "页头页脚用 header/footer 语义标签，别全 div，方便读屏和 SEO"

    CSS 变量 / 主题切换原理/ 改一个值，全站变色
    全站颜色不写死，而是存在 CSS 变量里。下面三个色板，分别控制三个变量：拖 --brand，主色相关的东西一起变；拖 --bg / --card，背景和卡片跟着变。暗色模式就是换了一整套变量值。
    --brand 主色按钮 / 链接 / 选中态
    --bg 页面背景整站底色
    --card 卡片背景卡片 / 弹窗底色
    选中标签
    上面三个色板各管一个变量，拖一下对应块就变——因为它们的颜色不是写死的，而是 var(--brand) 这类变量引用：改一处，所有引用它的地方一起变。这也解释了暗色模式为什么省事：不用改一百个组件，换一整组变量值就行。
    "改 --brand 主色，全站按钮链接实时变"
    M2 · JavaScript 与浏览器交互

    让页面根据数据和事件真正动起来

    先看变量、调用、数组和异步如何影响结果，再学会让 AI 修改交互代码时保留状态边界和事件行为。

    变量与作用域 Scope/ var · let · const
    先选一个关键字，看它能不能越过花括号以及能不能重新赋值。
    var 看函数边界，let / const 看块边界；const 是绑定不能换人，不代表对象内容不能改。
    "默认用 const，只有需要重新赋值时才用 let，避免意外覆盖"
    函数与 this/ 看调用方式，不看定义位置
    点一种调用方式，观察 this 指向谁。
    对象方法被拆出来或直接交给定时器时，隐含的 this 可能丢失；箭头函数通过闭包保留外层对象。
    "把对象方法交给 setTimeout 前，先确认 this 是否需要绑定"

    原始行程：杭州 · 3 天、苏州 · 2 天、南京 · 4 天
    map 保持数量，filter 可能变少，reduce 变成一个统计结果；三个方法都返回新结果，不直接改原数组。

      固定案例演示：输入框只做展示，流程按预设问题跑。真实 RAG 里这个问题会进入第 1 步的查询理解。
      查询阶段如上；一条完整的生产级 RAG 链路还包括前面这些环节——点开看：
      ① 文档导入与清洗▼
      攻略、游记、官方介绍从网页或 PDF 进来：去广告、去重、去乱码，统一成纯文本。垃圾进垃圾出——清洗质量直接决定检索质量。
      ② 切块 Chunking▼
      长文档切成带上下文重叠的段落（如每块 300 字、重叠 50 字）。块太大检索不准，块太小语义不完整，需要按内容类型调。
      ③ Embedding 与索引▼
      每个块过 Embedding 模型变成向量，连同原文存进向量库（Chroma/Milvus）。BM25 倒排索引也在这时建好——倒排索引就是「词 → 出现在哪些段落」的清单，像书后的关键词索引；知识更新要重新入库。
      ④ 引用来源与权限过滤▼
      生成的答案要标注「依据哪几篇文档」，能点回原文；检索阶段先按用户权限过滤可见文档，避免把无权内容拼进答案。
      ⑤ 评估与失败回退▼
      用标注好的「问题 → 应命中文档」测试集评估召回率；检索置信度太低时回退成兜底话术或人工推荐，别硬编。
      RAG = 先检索知识库、再把命中的内容拼进 Prompt 喂给大模型，让答案有依据、少胡说。毕设里用 BM25（关键词匹配算法）抓关键词、向量检索抓语义、重排把两路结果合并排序。
      "实现 RAG：BM25 + 向量检索双路召回，重排后拼接上下文再调大模型生成"

      M7 · 数据与存储

      数据怎样存得对、查得快

      依次探索表结构、事务、索引、缓存和分页。先判断数据要求，再让 AI 选择方案。

      SQLite 数据库/ 表就是 Excel 页签
      关系型数据库把数据存成一张张表，行 = 一条记录，列 = 字段。ORM（SQLAlchemy）让你用 Python 对象操作表，不用手写 SQL 字符串。
      "用 SQLite + SQLAlchemy 建三张表：用户、行程、景点，外键关联 user_id"
      事务 ACID/ 要么都成，要么都不成
      A 的余额¥100
      → 转 30 →
      B 的余额¥50
      点上面两个按钮对比：一个两边一起变，一个中途失败、整笔取消。
      正常：A 扣钱、B 加钱都成功，一起提交。失败：A 扣了但 B 加不了，事务回滚——A 自动加回来，两边都没变。ACID 就是这四条性质的首字母：原子性（要么全成要么全没）、一致性（转账前后两人总金额不变）、隔离性（并发转账互不干扰）、持久性（提交后断电也不丢）。
      "转账和扣库存放同一个事务，任何一步失败全部回滚"
      索引 Index/ 全表扫 vs 走索引
      先选数据量，再点按钮对比
      表里 10 万行：没索引就一行行扫，扫 10 万行花 120ms；有索引直接定位到那 1 行，0.3ms。索引就是书的目录，空间换时间。
      "WHERE 常用字段加索引，避免 SELECT 走全表扫描"
      Redis 缓存/ 命中 vs 未命中
      点查询看第一次和第二次的区别
      第一次：缓存没有，去数据库查，240ms；第二次：直接从内存拿，2ms。差 100 倍。所以热点数据先问缓存，没有再查库并写回缓存。
      "热点数据加 Redis 缓存，TTL 10 分钟，未命中再查数据库并写回"
      分页 Pagination/ 前端那个分页器到了后端变成什么
      1
      前端只发两个数字：page 和 size。后端把它翻译成 LIMIT ? OFFSET ?——offset = (page-1) * size。响应里除了本页 items，还要回 total / page_count / has_next，否则前端分页器画不出页码。注意两条保护：size 要在后端夹住上限（前端能改成 999999），page 越界返回空数组而不是报错。
      "列表接口支持分页，参数 page 和 size，size 最大 50，返回 items、total、page_count、has_next"
      M8 · 身份与权限

      确认身份，再检查访问边界

      认识登录凭证、接口限流、跨域和安全实践，检查每个请求是否有权访问目标数据。

      JWT 登录态/ 无状态认证
      登录成功后，这里会出现「盖章的通行证」——一段分成三截的 token。
      登录成功发一个 JWT（三截：header.payload.signature），之后每次请求带上它，服务器验「章」不查数据库——所以叫无状态。注意：localStorage 存 token 遇到 XSS 会被偷，安全要求高的场景改用 HttpOnly Cookie + CSRF 防护；token 还要考虑过期刷新与撤销。
      "登录接口返回 JWT，前端存起来，之后请求头带 Authorization: Bearer <token>"
      限流 Rate Limit/ 点太快会被拒
      剩余额度 10 / 10（每秒恢复 1 次）
      连续点：前 10 次正常，超过就返回 429 Too Many Requests。后端用计数器或令牌桶控制 QPS（每秒请求数），防止一个人把服务打挂。
      "接口加限流，每个用户每秒最多 10 次，超过返回 429"
      CORS 跨域/ 浏览器拦的，不是服务器报的错
      CORS 是浏览器的同源策略，不是服务器的报错：请求照样发出去，服务器也可能返回 200，但浏览器不给 JS 读响应——所以「Network 里 200，前端却报 CORS 错」是真的。带了自定义头（如 Authorization）会先自动发一次 OPTIONS 预检，预检没过，真实请求根本不会发出。
      "后端加 CORS 中间件：允许来源 https://trip.demo、允许 GET/POST、允许 Authorization 头，并处理 OPTIONS 预检"
      安全实践/ 生产环境必防的 3 个坑
      // 有漏洞的写法
      // 正确的写法
      生产环境安全不是"加个登录"就完了——SQL 注入、XSS、密钥泄露是最常见的三类。左边是攻击者怎么利用，右边是怎么防。原则：永远不信任用户输入，永远不用硬编码密钥。
      "后端用参数化查询防注入，前端输出转义防 XSS，密钥放环境变量"

      CI/CD 持续集成部署/ 从写代码到部署的完整流程
      改一下这步的结果： 选一个失败点，看它怎么挡住后面的步骤

      // 这一步在干什么
      这是从你写代码到用户用上的完整流程：分支开发 → 提 PR Review → CI 自动检查 → 合并 → CD 自动部署。不是只讲 CI/CD，而是讲整个工程化链路怎么跑通。

      故障排查思维/ 线上出问题了怎么定位
      故障现象：凌晨 2 点，监控告警——POST /api/orders 接口 P99 延迟（把 100 个请求的耗时从慢到快排，第 99 个的耗时，也就是最慢那 1% 的水平）从 200ms 涨到 8s，用户反馈"下单按钮点了没反应"。
      // 排查命令 / 步骤
      // 这步能发现什么、下一步干嘛
      根因：某次上线加了个 for 循环里查数据库（N+1 问题），订单列表有 50 个商品就查了 50 次 DB，连接池打满。修复：改成一次 IN 查询批量拿。
      线上故障别慌——先看监控确认影响面，再看日志找报错，然后复现或定位代码。排查顺序：监控 → 日志 → 代码 → 回滚。先止血（回滚/扩容），再查根因。监控看的是 P99 这类分位延迟，不是平均延迟——平均延迟会被大量快请求拉低，掩盖慢请求。
      "线上变慢先看 P99 监控，再 grep 错误日志，最后定位代码"

        M12 · AI 协作总结章 · 随时可查

        把一路用过的 AI 方法整理成体系

        AI 协作在每个模块和项目步骤中都已经练习过；学完整条技术线后，再用这一章把任务拆解、上下文、约束、审查、验收和排障归纳成自己的工作方法。

        每一步都用这套方法

        1. 用自己的话解释问题属于哪一层，先写一个判断。
        2. 给 AI 相关文件、当前行为与预期结果，要求先阅读再修改。
        3. 一次只推进一个功能，说明允许修改的范围。
        4. 检查代码差异，运行成功与失败场景，再决定是否接受。
        5. 失败时带上复现步骤、报错与最近改动，继续缩小问题范围。

        练习一：先拆任务

        需求：“给行程列表加筛选、分页和导出”。第一轮应该交给 AI 什么任务？

        先选一个，再查看判断。

        练习二：验收 AI 输出

        一次筛选功能改动后，至少要检查哪些证据？勾选你认为必要的项目。

        完成选择后提交，看看漏掉了哪些验收。

        练习三：给出故障证据

        现象：点击保存后页面一直转圈。哪一组信息最适合先交给 AI？

        点击保存 → 预期：保存成功并停止 loading → 实际：请求返回 422，页面没有显示字段错误 → 最近改动：把字段 city 改成了 destination
        先选一组说法。

        整理一次小任务

        出错时，把问题补充完整

        “页面坏了”缺少定位信息。说明：触发操作、预期结果、实际结果、错误原文、相关请求和最近改动。分享前去掉口令、令牌与私人数据。

        例子：接口成功，列表却是空白

        先比较接口响应里的字段与页面取值。例如响应是 items，页面却读取 data.list。把响应样例和读取代码一同交给 AI，要求先验证字段对应，再做最小修复；最后重测成功、空列表和请求失败三条路径。
